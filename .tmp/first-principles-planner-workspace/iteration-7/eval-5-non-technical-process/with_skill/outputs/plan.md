# Code Review 效率改进方案

**深度**: Deep — 反复出现的问题，已尝试的方案（指定 reviewer）无效，需要重新审视问题本身
**输入**: 用户描述的团队现状（8人团队，日均5-6个PR，平均3天merge）

---

## TL;DR

**问题不是"大家不愿意 review"，而是 review 在和所有人的其他工作竞争注意力，而且每次 review 的认知成本太高。** 指定 reviewer 没用，因为它只解决了"谁来做"，没解决"什么时候做"和"做起来有多累"。核心改进方向：缩小每次 review 的认知负担（小 PR + 结构化描述），建立固定的 review 时间槽（消除调度摩擦），用异步优先机制替代"等人有空"的被动模式。

---

## 行动方案

| 优先级 | 改动 | 工作量 | 风险 | 价值 |
|--------|------|--------|------|------|
| P1 | **建立每日 review 时间槽** — 全员每天固定两个30分钟窗口（如10:00和15:00）专门做 review，日历上 block 掉 | 0.5天落地 | 低 — 最坏情况是执行不到位，回到现状 | 高 — 直接消除"等人有空"的调度延迟 |
| P1 | **PR 大小硬限制** — 单个 PR 不超过 300 行改动（测试代码不计）；超过的必须拆分。在 CI 中加 size check 自动标记 | 1天（CI配置+团队沟通） | 中 — 某些重构场景天然较大，需要豁免机制 | 高 — review 认知成本与 PR 大小是超线性关系，拆小是杠杆最大的单一改动 |
| P2 | **PR 描述模板** — 必须包含：改了什么（一句话）、为什么改、怎么测的、reviewer 该重点看哪里。空模板不能提交 | 0.5天 | 低 | 中 — 降低 reviewer 的"启动成本"，不用先花 10 分钟搞清楚这个 PR 在干嘛 |
| P2 | **review 轮转制替代指定制** — 每天早上自动分配当天的 review 对（可用 GitHub Actions 或简单脚本），保证每个人每天最多 review 2 个 PR | 1天 | 中 — 需要处理领域知识匹配问题 | 中 — 把"谁来 review"从需要决策变成默认值，消除扩散责任 |
| P3 | **SLA + 可视化** — PR 超过24小时未首次 review 的，Slack/钉钉自动提醒；建立团队 dashboard 展示 review 周期趋势 | 1-2天 | 低 — 提醒频率需要调对，太频繁会被忽略 | 中 — 制造社会压力和透明度，但不解决根本原因 |
| P3 | **引入"快速通道"** — 纯重构、依赖升级、文档修改等低风险 PR 标记为 fast-track，只需 1 人 approve + CI 通过即可 merge | 0.5天 | 低 — 需要明确 fast-track 标准，防止滥用 | 低-中 — 减少队列中的 PR 总量，让有限的 review 精力集中在真正需要仔细看的 PR 上 |
| **合计** | | **约4-5天** | | |

**建议执行顺序**: P1 两项先落地（1.5天），运行一周观察效果。如果 merge 周期降到 1.5 天以内，P2/P3 按需补充。如果没有明显改善，说明问题根源不在流程而在团队文化或工作负载，需要重新诊断。

---

## 不要做什么

- **不要加更多审批层级**（如要求 2 人 approve）。问题是 review 太慢，加门槛只会更慢。
- **不要引入 AI 自动 review 工具来替代人工 review**。目前的瓶颈是人的注意力分配，不是 review 能力。AI review 可以作为辅助（提前发现明显问题），但不能替代人对业务逻辑和设计的判断。如果 AI review 让人产生"已经有人看过了"的错觉，反而会降低人工 review 的质量。
- **不要搞 review 积分/排名制度**。这类激励机制会导致"快速 approve 刷数量"的行为，最终 review 质量下降。

---

## 风险与缓解

| 风险 | 缓解措施 |
|------|----------|
| PR 大小限制导致拆分成本增加，开发者抱怨 | 前两周作为"建议"而非"强制"，收集拆分困难的具体案例，据此调整限制和豁免规则 |
| 固定 review 时间槽被跳过（"这个会更重要"） | 团队约定：review 时间槽优先级高于非紧急会议。前两周 lead 带头遵守，形成习惯后自然维持 |
| 轮转制导致不熟悉的人 review 不熟悉的模块 | 允许轮转 reviewer 主动拉领域专家做 secondary review，但首次响应仍由轮转 reviewer 负责（确保 SLA） |

## 自检

**核心问题**: 这个方案最可能的失败模式是什么？

最可能的失败模式是：**团队工作量本身就超载了**。如果 8 个人每天产出 5-6 个 PR，意味着每人每天平均要在自己写代码之外 review 约 1 个别人的 PR。如果每个 PR 的 review 需要 30-60 分钟，这已经占据了每天 10-15% 的工作时间。如果团队同时还有大量会议、on-call、支持工作，那 review 时间被挤压不是流程问题而是产能问题——任何流程优化都无法在不减少其他工作的前提下"变出"时间。

**如果我知道它会失败，我会怎么做**: 不改流程，直接减少在途 PR 数量——引入 WIP（Work In Progress）限制，每人同时最多 1 个 open PR，新的 PR 必须等前一个 merge 后才能开。这会强制团队从"个人推进速度最大化"转向"团队交付速度最大化"，因为你的 PR 不 merge，你就不能开新的，所以帮别人 review 变成了对自己有直接利益的事。

## 分析（Phase 1-2 推理过程）

### Phase 1: 问题考古

#### 五问法

1. **表面问题**: PR 平均 3 天才能 merge
2. **为什么?** → 没人及时 review
3. **为什么没人及时 review?** → 大家说忙——review 在和其他工作争夺注意力，review 总是输
4. **为什么 review 总是输?** → review 是帮别人的事，自己的 feature/task 有 deadline，review 没有
5. **为什么 review 没有 deadline?** → 因为组织里没有把 review 当作和写代码同等重要的"正式工作"来对待

**根因**: Review 在团队的优先级体系中是二等公民。它没有专属时间、没有明确的响应 SLA、没有可见的度量。指定 reviewer 只是分配了责任人，但没有改变 review 在优先级竞争中的地位。

#### 问题陈述

团队 PR merge 周期（平均3天）远超健康水平（❓ 行业参考值通常在4-24小时），导致开发者在等待中频繁 context switch、代码冲突增加、功能交付延迟。**已解决 = 80%的PR在24小时内完成首次 review，平均 merge 周期降到1.5天以内。**

#### 假设审计

| # | 假设 | 类型 | 如果错了... |
|---|------|------|-------------|
| 1 | "大家都很忙"是真实的——review 慢是因为没有空闲时间 | ❓ 未验证 — 可能是优先级问题而非时间问题 | 如果实际上有时间但缺乏动力，那需要改变激励结构而非时间安排 |
| 2 | 指定 reviewer 能解决责任扩散 | 惯例 — 已被证伪 | 已经失败了，说明问题不在"谁来做"而在"什么时候做"和"做起来多累" |
| 3 | 每个 PR 都需要同等深度的 review | 惯例 | 如果能分级处理，低风险 PR 走快速通道可以释放大量 review 精力 |
| 4 | PR 的 review 成本主要由代码复杂度决定 | ❓ 未验证 | 实际上"搞清楚这个 PR 在干嘛"的启动成本可能比"看代码"本身还高——PR 描述质量是关键杠杆 |
| 5 | 8个人5-6个PR/天的产出率是合理且不可减少的 | ❓ 未验证 | 如果产出率本身就超过了团队的消化能力，任何流程优化都是治标 |
| 6 | 需要保持当前的"每个PR至少2人approve"的规则 | ❓ 未验证 — 未确认团队是否有此规则 | 如果是单人 approve 就够了，review 负载直接减半 |

#### 真约束 vs 惯例

| 条件 | 类型 | 分析 |
|------|------|------|
| 代码必须被 review 后才能 merge | 真约束 | 质量保障的基本要求，不能取消 |
| 所有 PR 都需要相同深度的 review | **惯例** | 低风险改动（重构、文档、依赖升级）可以走快速通道 |
| Review 是"有空就做"的任务 | **惯例** | 可以变成有固定时间槽的正式工作 |
| 每个 PR 天然就是提交时的大小 | **惯例** | 可以通过大小限制和拆分规范主动控制 |
| Reviewer 需要从零理解 PR 上下文 | **惯例** | PR 描述模板可以大幅降低 reviewer 的启动成本 |

### Phase 2: 方案重构

#### 方案类别

**A: 减少 review 等待时间（调度优化）**
- 机制: 固定 review 时间槽 + 轮转分配
- 优势条件: 团队实际上有时间，只是 review 优先级被挤压
- 失败条件: 团队真的超载了，挤不出时间
- 挑战的惯例: "有空就 review" → "到点就 review"

**B: 减少单次 review 的认知成本（PR 侧优化）**
- 机制: 小 PR + 结构化描述 + 分级处理
- 优势条件: 当前 PR 偏大或描述不清，导致 reviewer 望而却步
- 失败条件: PR 已经很小且描述清晰，问题不在这里
- 挑战的惯例: "PR 大小由 feature 决定" → "PR 大小由 reviewability 决定"

**C: 减少需要 review 的总量（需求侧优化）**
- 机制: WIP 限制、合并低风险 PR 的快速通道
- 优势条件: 当前在途 PR 太多，超过团队消化能力
- 失败条件: 如果 PR 量本身不是问题
- 挑战的惯例: "个人产出速度最大化" → "团队交付速度最大化"

#### 推荐

**A + B 组合**，以 B 为主（减少认知成本）、A 为辅（固定时间槽）。

推理链:
1. 根因是 review 在优先级竞争中输给其他工作（Phase 1 五问法结论）
2. 固定时间槽直接解决优先级竞争（A → 满足根因）
3. 但即使有时间，如果每个 PR review 起来很费劲，固定时间槽内也做不了几个 → 需要 B 来降低单次成本
4. C（WIP限制）是更根本的解决方案，但实施阻力大（直接限制了个人产出速度），建议作为 P1 失效后的后备方案

#### 反转测试

**在什么条件下"固定 review 时间槽 + 小 PR"是最差方案？**

当团队的真正问题是技术能力差距大——少数人的代码只有他们自己能看懂。这种情况下，小 PR 和固定时间也没用，因为 reviewer 根本不具备理解代码的能力。如果这是实际情况，需要先解决代码可读性和知识分享的问题（结对编程、内部 tech talk），review 流程优化是次要的。

❓ 这一条件是否存在需要用户确认。
