# Write-Lock Enforcement: End-to-End Trace & Deployment Readiness Assessment

## Answer

The write-lock enforcement is architecturally sound for team deployment on Claude Code. It provides a genuine hard gate (exit 2 blocks the tool invocation), not advisory guidance. There are two specific gaps to address before team rollout: (1) governance marker blocking has no test coverage and silently degrades on jq-less environments, and (2) the fail-open design means a misconfigured environment silently disables enforcement rather than failing loudly. Both are fixable. The core mechanism is well-tested (40+ assertions) and the defense-in-depth with write-set enforcement, bash-guard, and post-write advisory tracking is meaningfully layered.

## End-to-End Flow

### 1. Registration: settings.json

The hook chain starts in `.claude/settings.json` (verified: read file), generated by `setup.sh:184-282`.

```
settings.json → hooks.PreToolUse → matcher "Edit|Write|MultiEdit|CreateFile|NotebookEdit"
                                 → command: ".baton/hooks/run-hook.cmd PreToolUse"
```

The matcher restricts which tool invocations trigger the hook. A second PreToolUse entry handles `Bash` (for `bash-guard.sh`). (verified: `.claude/settings.json:9-27`)

**IDE coverage:**
- **Claude Code / Factory**: Full enforcement via `settings.json` hooks. Exit code 2 = hard block. (verified: `settings.json:8-106`)
- **Cursor**: Reduced enforcement via `.baton/adapters/cursor/adapter.sh`. Translates exit 2 to `{"decision":"deny","reason":"..."}`. (verified: `adapter.sh:12-36`)
- **Codex**: No write-lock at all. The adapter explicitly documents: "Hard gates (write-lock, bash-guard) are not available on Codex." (verified: `codex/adapter.sh:8-10`). Codex relies on its sandbox model instead.

### 2. Bridge: run-hook.cmd (polyglot wrapper)

`.baton/hooks/run-hook.cmd` is a cmd.exe/bash polyglot. (verified: read file)

- On Windows: The batch portion finds Git Bash in standard locations (`C:\Program Files\Git\bin\bash.exe`, `%LOCALAPPDATA%\Programs\Git\bin\bash.exe`, PATH) and calls `dispatch.sh`. (verified: `run-hook.cmd:17-37`)
- On Unix: The bash portion does `exec bash dispatch.sh "$@"`. (verified: `run-hook.cmd:44-45`)
- **Edge case**: If no bash is found on Windows, it exits 0 silently (`exit /b 0` at line 40). This is a **fail-open** — hooks become no-ops without warning. The comment says "hooks are advisory, not blocking" which is inaccurate for write-lock specifically.

### 3. Dispatch: dispatch.sh

`dispatch.sh` (verified: read file) does event routing:

1. Buffers stdin into `BATON_STDIN` (line 20) so multiple hooks can read the JSON payload.
2. Extracts `tool_name` from stdin JSON via jq, with sed fallback (lines 25-31).
3. Reads `manifest.conf` line by line, matching `event:matcher:script` triples.
4. For PreToolUse with `Write,Edit,MultiEdit,CreateFile,NotebookEdit` matcher, dispatches to `write-lock` (i.e., `write-lock.sh`). (verified: `manifest.conf:4`)
5. Runs each hook in a subshell: `( . "$_dir/$_script.sh" )`. Exit code 2 = block; this propagates. (verified: `dispatch.sh:52-57`)

**Key detail**: `manifest.conf:4` uses comma-separated matchers (`Write,Edit,MultiEdit,CreateFile,NotebookEdit`). The dispatch matcher check is `case ",$_matcher," in *",$_tool,"*)` — this correctly handles comma-separated lists. (verified: `dispatch.sh:44-47`)

### 4. Core Enforcement: write-lock.sh

Version 3.1. 172 lines. (verified: read entire file)

#### Decision Flow

```
BATON_BYPASS=1?  ──yes──→  exit 0 (allow, warn to stderr)
        │no
        ▼
Resolve target path (BATON_TARGET env → stdin JSON .tool_input.file_path)
        │
Can't determine target?  ──yes──→  exit 0 (FAIL-OPEN, warn to stderr)
        │no
        ▼
Target is *.md / *.mdx?  ──yes──→  Check governance markers in content
        │no                         │
        │                     Contains BATON:GO/BATON:OVERRIDE?
        │                           │yes → exit 2 (BLOCK)
        │                           │no   → exit 0 (allow)
        ▼
Source common.sh / plan-parser.sh
        │
common.sh missing?  ──yes──→  exit 0 (FAIL-OPEN, warn)
        │no
        ▼
Target outside project root?  ──yes──→  exit 0 (allow)
        │no
        ▼
No plan file found?  ──yes──→  exit 2 (BLOCK: "Complete research first")
        │no
        ▼
Multiple plans, no BATON_PLAN?  ──yes──→  exit 2 (BLOCK: "ambiguous")
        │no
        ▼
Plan has <!-- BATON:GO -->?  ──no──→  exit 2 (BLOCK: "Annotation cycle")
        │yes
        ▼
Write-set defined in plan?  ──yes──→  Target in write set?
        │no                                │yes → exit 0 + additionalContext JSON
        │                                  │no  → exit 2 (BLOCK: "not in approved write set")
        ▼
exit 0 + additionalContext JSON
```

### 5. Plan Discovery: plan-parser.sh

`parser_find_plan()` (verified: `plan-parser.sh:35-140`) walks up from `JSON_CWD` (or `pwd`) looking for:
- `plan.md`, `plan-*.md` at each directory level
- `baton-tasks/*/plan.md`, `baton-tasks/*/plan-*.md`

Filters out `BATON:COMPLETE`-marked plans. Multi-plan disambiguation:
1. If exactly one plan has `BATON:GO` → select it (line 83-96)
2. If target is in `baton-tasks/<topic>/` → prefer that topic's plan (line 98-125)
3. Otherwise → `MULTI_PLAN_COUNT > 1` → write-lock blocks (fail-closed)

`parser_has_go()` is a simple grep: `grep -q '<!-- BATON:GO -->' "$_plan"` (verified: `plan-parser.sh:194-197`)

### 6. Write-Set Enforcement

When the plan has `BATON:GO`, write-lock additionally checks the write set (lines 150-161):

1. `parser_writeset_extract()` parses `Files:` fields from `## Todo` checklist items. Format: `` Files: `path/a.ts`, `path/b.ts` `` (verified: `plan-parser.sh:408-429`)
2. `parser_writeset_normalize()` strips `./`, converts absolute paths to project-relative, handles Windows drive letters via cygpath. (verified: `plan-parser.sh:373-401`)
3. If write set is non-empty and target is not in it → exit 2 (block).
4. If write set is empty (no `Files:` in Todo) → allow (no enforcement).

**Post-write advisory**: `post-write-tracker.sh` fires on PostToolUse and warns (stderr only, never blocks) if a written file isn't in the write set. Tracks repeat violations per session. (verified: read `post-write-tracker.sh`)

### 7. Complementary Gate: bash-guard.sh

`bash-guard.sh` (verified: read file) covers the Bash tool to prevent shell-based writes when the gate is closed:
- Blocks: output redirection (`>`), heredoc-to-file, `tee`, `sed -i`, `perl -pi`, `cp`, `mv`, `install`, `truncate`, `patch`, `python -c open('w')`
- Warns only: `rm`, `touch`
- Uses quote stripping to avoid false positives from echoed strings containing `>`
- When gate is open (`BATON:GO` present) → allows everything

## Edge Cases

### Governance Markers in Content

**What it does** (verified: `write-lock.sh:57-77`):
- For markdown targets only, if jq is available, extracts `new_string` (Edit) or `content` (Write) from stdin JSON.
- If the content contains `<!-- BATON:GO` or `<!-- BATON:OVERRIDE` → exit 2 (block).
- Files under `baton-tasks/` are exempted (they may reference markers as examples).

**Gaps identified:**

1. **jq dependency for governance check**: The governance marker check at lines 65-75 has `command -v jq >/dev/null 2>&1` as a guard. **Without jq, the entire governance marker check is silently skipped.** The awk fallback (lines 39-44) only handles `file_path` and `cwd` extraction — it does not extract `new_string` or `content` for marker scanning. This means on a jq-less system, the AI could write `<!-- BATON:GO -->` into a markdown file unchallenged. (verified: lines 65-75 — the `if` block only fires when jq is available; no awk fallback for content extraction exists)

2. **No test coverage**: There are zero tests for governance marker blocking in `test-write-lock.sh`. (verified: grepped for `governance|marker.*block|BATON:GO.*content|new_string.*BATON` in test file — no matches)

3. **Pattern matching is substring-based**: Uses bash `case` with `*'<!-- BATON:GO'*` — this would catch `<!-- BATON:GO -->`, `<!-- BATON:GO_EXTRA -->`, or even text discussing the marker in comments. The `baton-tasks/` exemption handles the most common false positive (plan documentation), but a markdown file outside `baton-tasks/` that discusses governance markers would be blocked from mentioning them.

4. **Only markdown files checked**: Source files (`.ts`, `.py`, etc.) are blocked entirely without GO, so governance markers in source files are a non-issue. But after GO is granted, there's no check on governance markers being injected into source file comments.

### Bypass Mode

**BATON_BYPASS=1** (verified: `write-lock.sh:17-20`):
- Checked before anything else — exits immediately with warning to stderr.
- Completely bypasses all checks including governance marker protection.
- Test coverage exists: Test 8 in `test-write-lock.sh` verifies both the allow behavior and the stderr warning. (verified: `test-write-lock.sh:169-191`)
- bash-guard does NOT check `BATON_BYPASS` — but this is moot because bash-guard also checks `parser_has_go` and won't block when the gate is open. However, it means BATON_BYPASS doesn't affect bash-guard's behavior when the gate is closed. (verified: no grep match for `BYPASS` in `bash-guard.sh`)

**Assessment**: BATON_BYPASS is environment-scoped, requires explicit `=1`, and emits a visible warning. Appropriate for emergency use. A team member setting it permanently would be visible in stderr logs.

### jq-less Environments

The codebase has three layers of jq fallback:

| Component | jq behavior | Fallback | Gap |
|-----------|------------|----------|-----|
| `dispatch.sh` tool_name extraction | jq first | sed fallback (line 29) | None observed |
| `write-lock.sh` target path | jq first | awk fallback (lines 39-44) | None — path extraction works |
| `write-lock.sh` governance markers | jq only (line 65) | **No fallback** | **AI can inject BATON:GO/BATON:OVERRIDE into markdown** |
| `bash-guard.sh` command extraction | jq first | awk fallback (lines 45-48) | None observed |
| `plan-parser.sh` functions | Pure awk/grep | N/A | Fully jq-independent |

**Test coverage for awk fallback**: Test 18 in `test-write-lock.sh` explicitly hides jq and verifies the awk path extraction works. (verified: `test-write-lock.sh:333-351`)

## Fail-Open vs Fail-Closed Analysis

The write-lock uses a mixed strategy:

| Condition | Behavior | Rationale |
|-----------|----------|-----------|
| Unexpected error (trap) | **Fail-open** | Don't block developer on hook crashes |
| Can't determine target | **Fail-open** + warning | Can't enforce what you can't identify |
| common.sh not found | **Fail-open** + warning | Infrastructure broken, don't block |
| No plan found | **Fail-closed** (exit 2) | Core enforcement |
| Plan without GO | **Fail-closed** (exit 2) | Core enforcement |
| Multiple plans, no selector | **Fail-closed** (exit 2) | Ambiguity resolved conservatively |
| Target outside project | Allow (intentional) | Only enforce within project boundary |
| No bash on Windows | **Fail-open** (silent) | run-hook.cmd line 40 |

**The fail-open cases are the primary deployment risk.** In a correctly configured environment, none of them fire. But they mean a partially broken installation silently degrades to no enforcement rather than failing visibly.

## Deployment Readiness Assessment

### Strengths (team deployment)

1. **Genuine hard gate**: Exit code 2 blocks the tool invocation at the IDE level. This is not advisory — Claude Code will not proceed with the write. (verified: Claude Code hook protocol documentation + exit code 2 handling in dispatch.sh)

2. **Defense in depth**: Three layers — write-lock (pre-write block) + bash-guard (shell write block) + post-write-tracker (drift detection). Each covers different bypass vectors.

3. **Write-set scoping**: Beyond just GO/no-GO, the plan's `Files:` field restricts which files can be modified. This is meaningful scope control.

4. **Multi-plan safety**: Ambiguous multi-plan scenarios fail-closed (exit 2), not fail-open. The disambiguation logic (GO uniqueness, baton-tasks context) is reasonable.

5. **Cross-platform**: Windows support via polyglot run-hook.cmd + cygpath normalization in write-set paths. Tested on Windows (per CLAUDE.md platform notes).

6. **Auditability**: All blocks emit descriptive stderr messages with phase guidance. Post-write-tracker creates violation logs in `/tmp/`.

### Weaknesses (blocking or material)

1. **Governance marker bypass without jq** (Material):
   Without jq, the AI can write `<!-- BATON:GO -->` into any markdown file, effectively self-granting write permission. This undermines the human-only authorization model.
   - **Severity**: High in jq-less environments. Most developer machines have jq, but CI or minimal containers may not.
   - **Fix**: Add awk-based content extraction for governance marker checking, matching the existing awk fallback pattern.

2. **Silent fail-open on missing bash** (Material for Windows):
   `run-hook.cmd` exits 0 (allow) if no bash is found, with no warning. On a Windows machine without Git Bash, all enforcement silently disappears.
   - **Severity**: Medium. Git Bash is nearly universal on developer Windows machines, but worth a startup check.
   - **Fix**: Have `setup.sh` verify bash availability at install time, or have `run-hook.cmd` write a warning to a log file.

3. **No integration tests for write-set enforcement or governance markers**:
   The primitives are tested, but the end-to-end path through write-lock.sh is not. A refactor could break the integration without any test catching it.
   - **Severity**: Low-medium. The code paths are simple (3-4 lines wiring primitives to exit codes), but test gaps are test gaps.

4. **Codex has no enforcement**: Explicitly documented but worth highlighting — teams using Codex get guidance only, no hard gates.

### Non-issues (investigated and dismissed)

- **Exit code propagation**: dispatch.sh correctly propagates exit 2 and only exit 2 as blocking. Other exit codes are logged as warnings but don't block. (verified: `dispatch.sh:54-61`)
- **BATON_STDIN buffering**: stdin is read once in dispatch.sh and exported. Hooks read from `BATON_STDIN`, not stdin. No race condition possible. (verified: `dispatch.sh:19-20`, `write-lock.sh:23-28`)
- **BATON:GO marker format**: Fixed string match `<!-- BATON:GO -->` via `grep -q`. Cannot be spoofed with similar-looking strings because the full HTML comment syntax is required. (verified: `plan-parser.sh:196`)
- **Path traversal**: Target paths are canonicalized via `realpath -m` / `readlink -f` before project-root containment check. `../` traversal is resolved. (verified: `write-lock.sh:94-132`, test 5b)

## Challenge

**Weakest conclusion**: That the governance marker check gap is "high severity." In practice, most development environments have jq installed. The real risk is minimal containers or CI environments, which are less likely to have an AI agent writing interactively.

**What would disprove it**: If Claude Code's hook system has its own content-inspection layer that catches governance markers independently of baton's check, the gap would be a non-issue. I found no evidence of such a layer — Claude Code's hook protocol is pass/fail based on exit code only.

**What I skipped**: I did not trace the `setup.sh` jq-based merge path for `settings.json` in detail (the non-jq install path). I did not investigate whether Claude Code sanitizes hook stderr output before displaying to the AI (relevant for injection via crafted error messages). I did not run the test suite to verify current pass/fail status.

## Recommendations for Team Deployment

**Blockers** (fix before rollout):

1. Add awk-based content extraction for governance marker checking in `write-lock.sh:65-75`. The pattern already exists for `file_path`/`cwd` extraction — extend it to `new_string`/`content`.

2. Add test cases for governance marker blocking (both jq and awk paths) and write-set enforcement integration in `test-write-lock.sh`.

**Improvements** (fix soon after):

3. Add a startup validation in `phase-guide.sh` (SessionStart hook) that warns if jq is not available — "Baton enforcement degraded: jq not found, governance marker protection disabled."

4. Consider making `run-hook.cmd` emit a warning file or stderr message when bash is not found, rather than silently exiting 0.

5. Add an integration test for write-set enforcement through `write-lock.sh` (plan with `Files:` field, target in/out of set).
