# Code Review 效率改进方案

## 问题诊断

### 现状数据

- 团队 8 人，每天 5-6 个 PR，PR 平均等待 3 天才能 merge
- 已尝试指定 reviewer，无效——大家反馈"忙"

### 根因分析

"指定 reviewer 但没效果"说明问题不在流程缺失，而在**激励结构和成本分配**上。逐层拆解：

**第一层：为什么 reviewer 不及时 review？**
- 因为 review 别人的 PR 对自己没有直接收益，但有实在的成本（打断当前工作、理解上下文、承担审批责任）。

**第二层：为什么"指定 reviewer"没用？**
- 指定只解决了"谁来做"，没解决"什么时候做"和"做了有什么好处"。没有时间承诺、没有可见性、没有反馈循环。被指定的人把 review 放在自己的待办最后面，因为自己的开发任务有明确的 deadline 而 review 没有。

**第三层：为什么 PR 要等 3 天？**
- 3 天 = 大约经过了 2-3 轮"我看到通知了但现在没空→明天再看→忘了→被催→看了一半→提了 comment→等回复→又忘了"的循环。这是典型的**异步沟通延迟叠加**。

**核心矛盾：Review 是团队公共品，但成本由个人承担、收益由他人获得。** 在没有机制对齐激励的情况下，理性个体会自然地把 review 优先级排在自己的产出任务之后。

---

## 改进方案

### 原则

1. 降低单次 review 成本（让它更容易做）
2. 建立时间承诺（让"什么时候做"有明确预期）
3. 让 review 成为可见的贡献（让做了有好处）
4. 缩短反馈循环（减少异步延迟叠加）

---

### 措施一：引入 Review SLA（时间承诺机制）

**做法：** 团队约定 PR review 的响应 SLA——被指定后 **4 个工作小时内**给出首次实质性反馈（不是"LGTM"也不是"稍后看"，而是真正的 review comment 或 approve）。

**为什么是 4 小时而不是更短：**
- 需要给 reviewer 一个合理的窗口来完成手头工作再切换
- 太短会导致频繁打断，太长又回到老问题
- 4 小时 = 上午收到的下午处理，下午收到的次日上午处理

**配套：**
- 在团队看板或 GitHub project board 上增加 "Awaiting Review" 列，标注进入时间
- 超过 SLA 的 PR 自动在日站会上可见（不需要 author 催人，机制自动暴露）

---

### 措施二：Review 时间块（降低上下文切换成本）

**做法：** 每人每天固定一个 30-45 分钟的 review 时间块。建议放在**午饭后**或**下午第一个时间段**——这是大多数人注意力不在巅峰、适合做 review 而不是创造性编码的时段。

**关键细节：**
- 这不是会议，是个人的专注时间块，日历上标注为"PR Review"
- 在这个时间块里只做 review，不写代码
- 8 个人 × 每天 30-45 分钟 = 团队每天 4-6 小时 review 产能，对应 5-6 个 PR 完全够用

**为什么有效：**
- 消除了"等有空再看"的模糊承诺——有固定时间就不需要找空
- 批量处理 review 比零散做效率高（减少上下文切换）
- 让 review 从"额外负担"变成"日常节奏的一部分"

---

### 措施三：缩小 PR 粒度（降低单次 review 成本）

**做法：** 设定 PR 大小的指导线——**单个 PR 不超过 300 行变更**（不含自动生成的文件）。超过的需要拆分。

**为什么这是关键杠杆：**
- 研究数据（Google、Microsoft 内部研究）一致显示：PR 越大，review 延迟越长，review 质量越低
- 一个 800 行的 PR 需要 reviewer 投入 45-60 分钟，这很难在碎片时间完成，所以一直被推迟
- 拆成 3 个 250 行的 PR，每个 15-20 分钟就能 review 完，容易塞进时间块里

**配套：**
- 可以用 GitHub Action 在 PR 创建时自动标注大小（S/M/L/XL）
- L 和 XL 的 PR 在日站会上讨论是否可以拆分

---

### 措施四：轮转指派 + 双人制（解决"指定 reviewer 不响应"）

**做法：** 放弃手动指定，改为自动轮转指派。每个 PR 指派 2 名 reviewer，任意 1 人 approve 即可 merge。

**为什么双人制：**
- 单人指派 = 单点故障。那个人真的忙的话，PR 就完全阻塞
- 双人指派 + 任一 approve = 冗余。两个人中至少有一个能在 SLA 内响应的概率远高于只指定一个人
- 同时保持了 review 覆盖率——不是降低标准，而是增加弹性

**工具：**
- GitHub 的 CODEOWNERS + 自动 review 分配（round-robin 模式）可以直接实现
- 或者用一个简单的 GitHub Action 做轮转

---

### 措施五：让 Review 贡献可见（激励对齐）

**做法：**

1. **周报/双周报中增加 review 指标：** 每人完成的 review 数量、平均响应时间。不作为 KPI 考核（避免激励扭曲），但作为**可见的贡献**展示。
2. **在团队回顾会上提及：** "本周 review 响应最快的是 XX，平均 2 小时"——正向反馈比惩罚有效。
3. **在 1-on-1 中纳入 review 作为"团队贡献"维度讨论：** 让大家意识到这不是"额外的事"，而是工程师职责的一部分。

**为什么不做强制考核：**
- 考核 review 数量会导致草率 approve（Goodhart's Law）
- 目标是让 review 成为正常节奏，不是制造对抗

---

### 措施六：Author 侧优化（降低 reviewer 理解成本）

**做法：** 要求每个 PR 包含：

1. **PR 描述模板：** 改了什么、为什么改、怎么测的（3 行够了，不要长篇大论）
2. **自 review 标注：** Author 在提交前自己过一遍 diff，对需要重点关注的地方加 comment（"这里逻辑比较绕，请重点看"）
3. **截图/录屏：** 如果是 UI 变更，附上前后对比

**为什么有效：**
- Reviewer 最大的隐性成本是"理解这个 PR 在干嘛"。好的描述可以把 review 时间从 30 分钟降到 15 分钟
- Author 的自 review 标注是在利用信息不对称——Author 最知道哪里容易出问题

## 实施路径

### 第一周：低成本快速见效

| 行动 | 负责人 | 预期效果 |
|------|--------|----------|
| 团队会议达成 4 小时 SLA 共识 | 你 | 建立明确预期 |
| 每人日历上添加 review 时间块 | 全员 | 立即减少"没空"借口 |
| PR 描述模板添加到仓库 | 你 | 降低 review 门槛 |

### 第二周：机制落地

| 行动 | 负责人 | 预期效果 |
|------|--------|----------|
| 配置自动 review 轮转分配 | 你 | 消除手动指派的摩擦 |
| 添加 PR 大小标签 Action | 任一成员 | 让大 PR 可见 |
| 看板增加 "Awaiting Review" 列 | 你 | 让等待可见 |

### 第三周起：观察 + 调整

| 行动 | 负责人 | 预期效果 |
|------|--------|----------|
| 收集 SLA 达标率数据 | 你 | 量化改进 |
| 回顾会讨论 review 节奏 | 全员 | 持续优化 |
| 根据数据调整 SLA / 时间块长度 | 你 | 适配团队实际 |

---

## 预期效果

如果以上措施落地，保守估计：

- **PR 等待时间从 3 天降到 1 天以内**（SLA + 时间块 + 双人制的组合效果）
- **Review 质量不下降甚至提升**（小 PR + 好描述 = reviewer 能真正理解代码）
- **团队摩擦减少**（不再需要 author 催人，机制自动推动）

最重要的心智转变：**Review 不是"帮别人的忙"，而是"团队交付速度的基础设施"。** PR 等 3 天意味着每个功能的交付周期至少多 3 天，8 个人 × 3 天的等待 = 大量的 WIP 堆积和上下文切换。加速 review 不是给个人加负担，而是让整个团队的吞吐量提升。
