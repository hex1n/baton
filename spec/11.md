Java 后端多 Agent Harness —— 最终设计 v1.0
综合全部讨论，以下是完整设计。

---

一、设计原则
P1: 方向 > 速度 —— 搞清楚做什么，比快速写代码重要
P2: 确定性优先 —— 能用编译器/测试验的不用 AI 判断
P3: 独立评估 —— Evaluator 从需求端推导预期，不从代码端推导
P4: 不可逆操作必须人类审批 —— migration、安全策略、外部集成
P5: 记录 Why —— 代码记录 What，文档记录 Why 和 Why Not
P6: 适应 Java 特性 —— 构建慢则分批，Spring 有魔法则运行时验证
P7: 支持存量代码 —— 不假设 greenfield

Agent 1: Explorer（仅存量项目）
触发条件：项目已有代码
目标：让后续 Agent 不用自己啃源码，节省上下文


输入： 现有代码库

工作步骤：
扫描项目结构（模块、包、分层）
分析依赖关系（pom.xml / build.gradle）
提取所有 REST 端点（扫描 @RequestMapping 等注解）
提取数据库表结构（读 Entity 类或 migration 文件）
识别 Spring 配置特殊点（自定义 AutoConfig、Profile、条件装配）
标注代码风格约定（命名规则、异常处理方式、日志习惯）
标注已知地雷区（高耦合模块、TODO/FIXME/HACK 注释）

输出： codebase-map.md

# 代码地图

## 项目结构
- 构建工具：Maven / Gradle
- Java 版本：17
- Spring Boot 版本：3.2.x
- 数据库：MySQL 8.0 + MyBatis-Plus

## 模块依赖
user-service → common-lib
order-service → user-service, common-lib
gateway → user-service, order-service

## 现有 API 清单（共 47 个端点）
| 路径 | 方法 | Controller | 描述 |
|------|------|-----------|------|
| /api/users | GET | UserController | 用户列表 |
| /api/users/{id} | GET | UserController | 用户详情 |
| ... | ... | ... | ... |

## 数据库表（共 12 张）
| 表名 | 核心字段 | 关联 |
|------|---------|------|
| t_user | id, name, phone, status | - |
| t_order | id, user_id, amount, status | → t_user |
| ... | ... | ... |

## Spring 配置要点
- 使用自定义 HandlerInterceptor 做鉴权
- Redis 缓存用 @Cacheable，key 规则：类名:方法名:参数
- 异步任务用 @Async + 自定义线程池 "taskExecutor"
- 多环境配置：dev / test / prod，通过 spring.profiles.active 切换

## 代码风格约定
- 包结构：controller / service / mapper / entity / dto / vo
- 统一返回格式：Result<T> { code, message, data }
- 异常处理：@RestControllerAdvice 全局捕获
- 日志：SLF4J，关键操作用 INFO，异常用 ERROR + 堆栈

## 地雷区 ⚠️
- OrderService.createOrder() 有 200+ 行，高度耦合
- t_product 表没有乐观锁字段，并发扣库存有风险
- common-lib 中的 DateUtils 有时区 bug（TODO 标注但未修复）

# 技术决策记录

## D1: 触发检查——同步调用，不用事件驱动
选择：在 OrderService.createOrder() 中直接调用 StockAlertTriggerService
不选：发领域事件 / 用 MQ 异步消费

Why：
- 当前系统没有事件总线基础设施
- 预警检查逻辑简单（一次查询 + 一次比较），不值得引入 MQ
- 异步方案需要考虑消息丢失、重复消费，复杂度不匹配

Why Not 事件驱动：
- 不是不好，是当前场景投入产出比不划算
- 如果未来触发点从 1 个变成 10 个，再考虑重构为事件驱动

## D2: 防重发——用数据库记录，不用 Redis
选择：t_stock_alert_log 表记录最后预警时间，查询判断是否在 1 小时内
不选：Redis SET NX + TTL 1 小时

Why：
- 项目当前 Redis 主要用于缓存，没有做持久化
- 如果 Redis 重启，防重发状态丢失，会导致重复预警
- 数据库方案虽然多一次查询，但可靠性更高
- 预警触发频率低（不是高并发场景），数据库完全扛得住

## D3: 在 OrderService 中的切入方式——直接调用，不用 AOP
选择：在 createOrder() 扣库存成功后直接调用 triggerService.check()
不选：用 AOP 切面自动拦截

Why：
- OrderService.createOrder() 已经 200+ 行（地雷区）
- AOP 切面会让代码流程更隐蔽，增加理解难度
- 直接调用虽然"不够优雅"但可读性最好
- 加一行代码 vs 新增一个切面类 + 切点配置 → 选简单的

## D4: 刻意不做的事情（不是遗漏）
- 不做预警规则引擎（需求只有固定阈值，不需要复杂规则）
- 不做预警聚合（需求确认每个商品独立预警）
- 不做预警确认/关闭功能（需求未提及，不过度设计）

Agent 4: Generator
目标：按模块实现代码
工作单元：模块（Bounded Context），不是时间（Sprint）


输入： requirements.md + architecture.md + decisi
ons.md + codebase-map.md

每个模块的执行流程：

1. 读取当前模块的范围（architecture.md 中的模块定义）
2. 读取相关的需求（requirements.md 中的对应功能点）
3. 读取决策记录（decisions.md 中的技术选型）
4. 分批生成代码：
   ┌─ 第 1 批：Entity + Mapper + Migration
   │  → 编译
   │  → 修复（如有错误）
   │
   ├─ 第 2 批：Service 层
   │  → 编译 + 单元测试
   │  → 修复
   │
   └─ 第 3 批：Controller + DTO/VO + 集成测试
   → 编译 + 全量测试
   → 修复

5. git commit "[module-name] 实现完成"
6. 交给 Evaluator


分批策略的原因（适应 Java）：
每批 3-5 个相关文件，一次编译
同层文件一起写（比如所有 Entity 一起），减少编译次数
不是逐文件编译（太慢），也不是整个模块一次性写完（错误累积）

上下文重置策略：

每个模块完成后，清空上下文，新模块启动时只读取：

必读：
- requirements.md（当前模块相关部分）
- architecture.md（当前模块定义 + 依赖模块的接口）
- decisions.md（所有决策，确保不违反已定方向）

按需读：
- 已完成模块的接口签名（Service 接口，不读实现）
- codebase-map.md 中和当前模块有交互的部分

不读：
- 已完成模块的实现细节
- 不相关模块的代码


Generator 的约束规则：
1. 不修改 decisions.md 中已决定的技术方案
2. 如果发现 architecture.md 的设计有问题：
   → 不自己改，而是在 generator-feedback.md 中提出
   → 等 Architect 或人类决定是否调整
3. 遇到存量代码地雷区（codebase-map.md 中标注的）：
   → 最小化改动，不做顺便重构
4. Migration 脚本只生成草案，标注 ⛔ 需要人类审批
   Agent 5: Runtime Evaluator（独立 Agent，独立上下文）
   目标：独立验证 Generator 的产出，从需求端推导预期
   关键：和 Generator 使用不同的 prompt、不同的上下文


输入：

# 八、错误恢复机制

场景 1：Generator 编译失败
  → 读编译错误 → 修复 → 重新编译
  → 3 次仍失败 → git reset 到上一个检查点 → 重新生成该批文件
  → 仍然失败 → 上报人类

场景 2：Evaluator 发现阻塞性问题
  → 写 evaluation-report.md → Generator 修复 → 重新评估
  → 3 轮仍不通过 → 上报人类（检查点 #E）

场景 3：Generator 发现架构设计有问题
  → 不自己改，写 generator-feedback.md
  → 暂停当前模块
  → 等 Architect 重新评估或人类决定

场景 4：测试通过但运行时信号异常（如 N+1）
  → 标记为警告，不阻塞
  → 所有模块完成后统一处理性能问题
  → 除非严重到影响功能（如超时）才阻塞

场景 5：Migration 执行失败
  → 回滚 migration
  → 上报人类（不自动修复 migration）

git 检查点策略：
  每批文件写完编译通过 → git commit
  每个模块 Evaluator 通过 → git tag module-N-done
  方便在任何节点回滚到已知好的状态

十、适用范围与局限
✅ 适合：
- 需求相对明确的业务系统（CRUD+、工作流、集成）
- 中等复杂度（3-10 个模块）
- 技术栈标准（Spring Boot 全家桶）
- 团队有明确的代码规范

⚠️ 需要调整：
- 高并发系统 → Evaluator 需要加压测层
- 微服务 → 每个服务独立跑一遍 harness + 加跨服务集成测试
- 复杂算法 → Specifier 需要定义算法验证标准（不只是 API 级别）

❌ 不太适合：
- 探索性项目（需求完全不明确，边做边想）
- 纯算法/数据处理（没有 API 层，Evaluator 的三层模型不适用）
- 对已有巨型系统的大规模重构（Explorer 的输出可能不够，需要人类深度参与）


以上是完整设计。核心理念：在正确的层次用正确的工具——确定性问题用确定性工具，需要创造力的问题用 AI，不可逆的决策用人类。
