# Research: Write-Lock Mechanism Across IDE Adapters

## Frame

- **Question**: Does the write-lock mechanism fire in all supported IDEs (Claude Code, Cursor, Codex), and what are the behavioral differences in enforcement?
- **Why**: The user is considering adding a new IDE adapter and needs to understand the common contract that adapters must satisfy.
- **Scope**: Write-lock hook invocation path, adapter translation layers, enforcement tiers, and the contract each adapter fulfills.
- **Out of scope**: Other hooks (phase-guide, bash-guard, etc.) except where they clarify the write-lock story. Internal write-lock logic (plan parsing, GO marker detection) is treated as a black box -- the focus is on the adapter layer.

## Orient

- **System familiarity**: partial -- I have read the hook system and adapter code during this session but have not worked in this codebase before.
- **Evidence type**: codebase-primary
- **Strategy**: Trace the write-lock invocation path for each IDE from hook registration (settings/config files) through dispatch to the write-lock script. Compare adapter behaviors in a table. Identify the common contract.

**1. What does this system do?**

Baton is a plan-first governance protocol for AI coding assistants. Its write-lock hook prevents source code modifications until a plan file contains the `<!-- BATON:GO -->` marker. It supports Claude Code, Factory, Cursor, and Codex as IDE targets. `setup.sh` installs the appropriate hook registration for each IDE. ✅ `read setup.sh:18, ide-capability-matrix.md:1-11`

**2. How is it organized?**

- `.baton/hooks/` -- core hook scripts (write-lock.sh, dispatch.sh, manifest.conf, lib/)
- `.baton/adapters/cursor/` -- Cursor-specific adapter and dispatch
- `.baton/adapters/codex/` -- Codex-specific adapter and dispatch
- `.claude/settings.json` -- Claude Code / Factory hook registration
- `.cursor/hooks.json` -- Cursor hook registration (generated by setup.sh)
- `.codex/hooks.json` -- Codex hook registration (generated by setup.sh)
- `setup.sh` -- installer that configures all IDEs

✅ `read setup.sh:148-182, glob .baton/adapters/`

**3. What are the key abstractions?**

- **Event types**: `PreToolUse`, `PostToolUse`, `SessionStart`, `Stop`, etc. -- defined in `manifest.conf`
- **Matchers**: filter which tool names trigger a hook (e.g., `Write,Edit,MultiEdit,CreateFile,NotebookEdit`)
- **dispatch.sh**: central dispatcher that reads `manifest.conf` and runs matching hooks in subshells
- **Adapters**: IDE-specific wrappers that translate between the IDE's hook protocol and dispatch.sh's exit-code-based protocol

✅ `read dispatch.sh:1-64, manifest.conf:1-12`

**4. How does data flow for a write-lock check?**

IDE triggers a hook event (e.g., PreToolUse for a Write tool call) -> IDE-specific registration invokes the appropriate entry point -> dispatch.sh buffers stdin, extracts tool_name, iterates manifest.conf -> write-lock.sh runs: determines target file, checks if markdown (allowed), finds plan, checks BATON:GO marker, enforces write-set -> returns exit 0 (allow) or exit 2 (block) -> adapter translates to IDE protocol.

✅ `read dispatch.sh:35-62, write-lock.sh:1-171`

## Investigation

### Move 1: Claude Code / Factory write-lock path

- **Question**: How does write-lock fire in Claude Code?
- **What was checked**: `.claude/settings.json`, `run-hook.cmd`, `dispatch.sh`, `manifest.conf`
- **What was found**:
  - Registration: `.claude/settings.json` registers `PreToolUse` with matcher `Edit|Write|MultiEdit|CreateFile|NotebookEdit` -> runs `.baton/hooks/run-hook.cmd PreToolUse` ✅ `read .claude/settings.json:9-16`
  - `run-hook.cmd` is a polyglot (bash + cmd.exe). On Windows, finds Git bash and calls `dispatch.sh`. On Unix, calls `dispatch.sh` directly. ✅ `read run-hook.cmd:1-45`
  - `dispatch.sh` buffers stdin (JSON from Claude Code containing `tool_name` and `tool_input`), reads `manifest.conf` line 4 (`PreToolUse:Write,Edit,MultiEdit,CreateFile,NotebookEdit:write-lock`), matcher matches, runs `write-lock.sh` in a subshell. ✅ `read dispatch.sh:35-52`
  - Write-lock exit code 2 propagated directly -- Claude Code interprets exit 2 as "block the tool call". ✅ `read dispatch.sh:54-56`
  - When allowed with BATON:GO, write-lock emits `hookSpecificOutput` JSON with `additionalContext` on stdout, which Claude Code displays to the AI as a reminder. ✅ `read write-lock.sh:162-165`
- **Enforcement**: **Hard block**. Exit 2 prevents the tool call from executing.
- **What remains unresolved**: Factory is treated identically to Claude Code (same settings.json format, same code path in setup.sh lines 661-665). ✅ `read setup.sh:661-665`

### Move 2: Cursor write-lock path

- **Question**: How does write-lock fire in Cursor?
- **What was checked**: `setup.sh` `generate_cursor_hooks()`, `.baton/adapters/cursor/dispatch.sh`, `.baton/adapters/cursor/adapter.sh`
- **What was found**:
  - Registration: `setup.sh` generates `.cursor/hooks.json` with `preToolUse` entries for Write, Edit, Bash matchers, each calling `bash .baton/adapters/cursor/dispatch.sh preToolUse`. ✅ `read setup.sh:286-318`
  - **Cursor uses camelCase** event names (`preToolUse`, not `PreToolUse`). The Cursor dispatch adapter maps these to PascalCase before calling `dispatch.sh`. ✅ `read .baton/adapters/cursor/dispatch.sh:11-21`
  - Cursor dispatch runs `dispatch.sh` and captures combined stdout+stderr. If exit code is 2, emits `{"decision":"block","reason":"..."}`. Otherwise emits `{"decision":"allow"}`. ✅ `read .baton/adapters/cursor/dispatch.sh:23-33`
  - The older `adapter.sh` (still present) takes a different approach: it calls `write-lock.sh` directly rather than going through dispatch.sh. It also uses `"deny"` instead of `"block"`. ✅ `read .baton/adapters/cursor/adapter.sh:12-36`
  - Capability tier header: Cursor deny messages include `[Baton capability: reduced enforcement (Cursor)]` prefix. ✅ `read .baton/adapters/cursor/adapter.sh:27,34`
  - Missing matchers vs Claude Code: Cursor's hooks.json does **not** register `MultiEdit`, `CreateFile`, or `NotebookEdit` matchers (only Write, Edit, Bash). ✅ `read setup.sh:298-306`
- **Enforcement**: **Hard block** via JSON protocol. The block is real, but the matcher coverage is narrower.
- **Boundary behaviors**:
  - `MultiEdit`, `CreateFile`, `NotebookEdit` tool calls would **not** trigger write-lock in Cursor (missing matchers). If Cursor supports these tools, writes through them bypass governance.
  - Two adapter files exist (`adapter.sh` and `dispatch.sh`). The setup.sh installer uses `dispatch.sh`. `adapter.sh` appears to be legacy.

### Move 3: Codex write-lock path

- **Question**: Does write-lock fire in Codex?
- **What was checked**: `setup.sh` `configure_codex()`, `.baton/adapters/codex/dispatch.sh`, `.baton/adapters/codex/adapter.sh`, `.codex/hooks.json` (generated format)
- **What was found**:
  - **Codex does NOT have a PreToolUse event.** The adapter comment states this explicitly: "Not available: write-lock (no PreToolUse hard gate)". ✅ `read .baton/adapters/codex/adapter.sh:7-8`
  - Codex hooks.json registers only `SessionStart` and `Stop` events. ✅ `read setup.sh:389-417`
  - The Codex dispatch adapter handles only `SessionStart` and `Stop`. All other events are passed through but there is no IDE-level registration to trigger them. ✅ `read .baton/adapters/codex/dispatch.sh:14-32`
  - SessionStart prepends a tier header: `[Baton capability: rules + guidance only (Codex)] Hard gates (write-lock, bash-guard) are not available.` ✅ `read .baton/adapters/codex/dispatch.sh:12`
  - **Write-lock is never invoked for Codex.** The governance relies on rules loaded via `AGENTS.md` referencing `constitution.md`, plus Codex's own sandbox/human approval controls. ✅ `read .baton/adapters/codex/adapter.sh:10-11, setup.sh:364-378`
- **Enforcement**: **None**. Advisory rules only.

### Common Contract for a New Adapter

Based on the patterns observed, a new adapter must:

1. **Map IDE events to dispatch.sh events.** The IDE may use different naming conventions (e.g., camelCase). The adapter translates. ✅ `read cursor/dispatch.sh:11-21`

2. **Handle stdin buffering.** dispatch.sh reads stdin once via `BATON_STDIN`. The adapter must pass through the IDE's stdin JSON or close stdin to prevent hangs (Codex pattern). ✅ `read .baton/adapters/codex/dispatch.sh:16, dispatch.sh:17-20`

3. **Translate exit codes to IDE protocol.** dispatch.sh exit 0 = allow, exit 2 = block. The adapter converts to whatever protocol the IDE uses (JSON, text, etc.). ✅ `read cursor/dispatch.sh:27-33`

4. **Register matchers for all write tools.** The full set is: `Write, Edit, MultiEdit, CreateFile, NotebookEdit`. Cursor currently only registers Write and Edit, creating a coverage gap. ✅ `read setup.sh:298-306 vs settings.json:11`

5. **Declare capability tier.** Prepend a `[Baton capability: ...]` statement so the AI knows the enforcement level. ✅ `read cursor/adapter.sh:27, codex/dispatch.sh:12`

6. **Add setup.sh integration.** A new `configure_<ide>()` function in setup.sh, plus detection in `detect_ides()`. ✅ `read setup.sh:84-100, 660-674`

7. **Add skill junctions.** setup.sh must junction `.baton/skills/*` into the IDE's skill directory. ✅ `read setup.sh:143-182`

### Where findings are in tension

- **Cursor has two adapter files** (`adapter.sh` and `dispatch.sh`). `adapter.sh` calls write-lock.sh directly and uses `"deny"` in JSON. `dispatch.sh` calls `dispatch.sh` (the central dispatcher) and uses `"block"` in JSON. Setup.sh installs `dispatch.sh`. The `adapter.sh` may be legacy or used in a different context. ✅ confirmed `adapter.sh` header says "Cursor JSON protocol", `dispatch.sh` header says "Cursor adapter for dispatch.sh"

- **Cursor matcher gap.** `setup.sh` registers Write and Edit but not MultiEdit/CreateFile/NotebookEdit for Cursor's `preToolUse`. This means files created via CreateFile or edited via MultiEdit in Cursor would bypass write-lock. Whether Cursor supports these tools is an open question (❓).

## Counterexample Sweep

- **Leading interpretation**: Write-lock provides hard enforcement in Claude Code and Cursor, but not in Codex.
- **Disproving evidence sought**: A path where Codex could fire write-lock, or where Claude Code could bypass it at the adapter level.
- **What was checked**: Searched Codex adapter files for any reference to `write-lock` or `PreToolUse`. Found the adapter comment explicitly stating "Not available: write-lock (no PreToolUse hard gate)". ✅ `read .baton/adapters/codex/adapter.sh:8`. Searched Claude Code path for any bypass other than `BATON_BYPASS=1` env var -- found the fail-open trap on unexpected errors (line 14) and the fail-open on missing target (line 49-54), both of which are safety mechanisms, not adapter-level bypasses. ✅ `read write-lock.sh:13-14, 48-54`
- **Result**: No evidence found that Codex can fire write-lock. Claude Code fail-open paths are internal to write-lock.sh, not adapter-level.
- **Effect on confidence**: High confidence in the tiered enforcement model.

## Final Conclusions

**C1**: Write-lock fires as a hard block in Claude Code / Factory (exit code 2) and Cursor (JSON block response), but **does not fire at all in Codex** due to missing PreToolUse event support.
- **Confidence**: High -- verified by reading all adapter source code and setup.sh registration.
- **Evidence**: `adapter-codex.sh:7-8`, `dispatch-codex.sh:14-32`, `settings.json:9-16`, `cursor/dispatch.sh:23-33`
- **Verification path**: Run `test-write-lock.sh` and `test-adapters-v2.sh` to confirm Claude Code and Cursor paths. Codex absence verified by code inspection.
- **Uncertainty**: Factory assumed identical to Claude Code (not independently tested).
- **Plan implication**: actionable -- a new adapter must determine whether its IDE supports PreToolUse-equivalent events.

**C2**: The common adapter contract requires: event name mapping, stdin handling, exit-code-to-protocol translation, tool matcher registration, capability tier declaration, and setup.sh integration.
- **Confidence**: High -- derived from the intersection of two working adapters.
- **Evidence**: Cursor and Codex adapters provide two concrete implementations of the pattern.
- **Verification path**: A new adapter following this contract should pass `test-adapters-v2.sh`-style verification.
- **Uncertainty**: Whether all six elements are truly required or some are optional conventions.
- **Plan implication**: actionable -- use as the checklist for new adapter development.

**C3**: Cursor has narrower matcher coverage than Claude Code (missing MultiEdit, CreateFile, NotebookEdit), creating a potential enforcement gap.
- **Confidence**: Medium -- the gap exists in registration, but whether Cursor supports those tools is unverified.
- **Evidence**: `setup.sh:298-306` vs `.claude/settings.json:11`
- **Verification path**: Check Cursor's documentation for supported tool types in its hooks system.
- **Uncertainty**: Whether Cursor exposes MultiEdit/CreateFile/NotebookEdit as hookable tools. ❓
- **Plan implication**: watchlist -- verify before deciding whether a new adapter needs these matchers.

**C4**: Two Cursor adapter files exist (`adapter.sh` and `dispatch.sh`) with slightly different behavior (`"deny"` vs `"block"`, direct call vs dispatch). Setup.sh installs `dispatch.sh`.
- **Confidence**: High -- verified by reading both files and setup.sh.
- **Evidence**: `adapter.sh:33-34` uses `"deny"`, `dispatch.sh:30` uses `"block"`, `setup.sh:287` uses dispatch.sh.
- **Verification path**: Search for any reference to `adapter.sh` in configuration files.
- **Uncertainty**: Whether `adapter.sh` is dead code or serves another purpose.
- **Plan implication**: watchlist -- clean up or document the legacy adapter.
