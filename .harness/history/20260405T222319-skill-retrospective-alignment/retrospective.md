## 4. Repo-Specific Lessons

- **Python `str.replace` substring-matches across markdown heading levels.** Trigger: any test that wants to modify a level-2 heading but leaves level-3 headings (or vice versa) untouched. `text.replace('## Foo', '## Bar')` will ALSO match `### Foo` because `## Foo` is a substring of `### Foo`. Takeaway: for heading-targeted test injections, use line-exact matching — `.splitlines()` then iterate and compare full-line equality, or anchor the regex with `^` and `$`. String `.replace()` is unsafe for any markdown/structured-text manipulation where prefixes of different lengths exist in the same file. Why: this cost one debug cycle on AC-6 and made the initial test result look like the guard was broken when it wasn't.
- **Design validator error output to localize the problem before it's asked to.** When Check 7 detected drift, it printed the full Expected list and full Actual list side-by-side — the difference was visible in one glance, no second query needed. Takeaway: for any checker that compares two structured objects (ordered lists, tables, heading sequences), always print both sides in the error message, not just "mismatch detected". The marginal cost is 10 lines of bash; the marginal benefit is halving debug turnaround.

## 5. Harness Lessons

> Same non-obvious bar as §4, but scoped to the baton harness itself.
> Empty is acceptable — don't pad.

- **`validate-artifact.sh` and `check-lesson-index-consistency.sh` are complementary, not redundant.** The validator runs per-artifact-write (via `post-artifact` hook) and catches missing sections in the live file at write time; the consistency checker runs per-commit and catches drift between files that don't write together (skill vs template vs protocol doc). A missing section in `retrospective.md` is a validator problem; a heading rename in the skill that breaks the extractor contract is a consistency-check problem. Takeaway: when adding a new guard for a harness feature, classify the failure mode first — "single-file missing content" → validator case; "multi-file contract drift" → consistency check. Picking wrong means the guard fires at the wrong time (too early, too late, or never).
- **Skill frontmatter `description:` is free real estate for dual-purpose documentation.** It's LLM-facing (trigger matching + role selection) but has no protocol-layer parser downstream of it, so you can pack it with context — in this task, two sentences in `description:` now encode the "close task + feed lessons.md" dual responsibility at zero validator cost. Takeaway: when a skill's role expands beyond its original purpose, update `description:` FIRST (before rewriting the body) — it's the cheapest place to declare the new scope, and it's what the role-selection logic reads. Updating only the body leaves the frontmatter as misleading documentation for future readers.
- **"Low-risk" is not a license to skip strict isolation in a repo that dogfoods strict.** I argued inline that this task was grep/diff/awk-only, so compat mode was "defensible" — and on *correctness* grounds it was. But the repo's entire `.harness/history/` precedent is that every task, including trivial ones, runs strict via `baton-verifier` / `baton-evaluator` subagents. The Stop hook caught me only because `provenance_normalize_value` rejected my multi-word Isolation mode string — if I had written a clean `compat` value with `sequential_fallback` context, the hook would have still blocked on "profile expects strict", but *later*, at a less visible moment. Takeaway: in this repo, the decision to downgrade to compat is a *policy* decision requiring `.harness/profile.local.yaml`, not a per-task convenience call. If you believe a task warrants compat, create the profile file explicitly — don't write `compat` inline and hope the hook is lenient. The "argue low-risk" reflex is a natural-language shortcut that the enum-valued protocol does not accept. Why: in this task the shortcut cost one full subagent re-run to retroactively produce a strict `verification.md` + `evaluation.md`; the work saved by going inline (~5 minutes) was dwarfed by the re-run cost (~8 minutes) plus the thread overhead.

## 6. Standardization Candidates

- **Check 8 candidate**: add a consistency check that verifies skill Step 3 prose section titles match the skill's own Output Template block. Current Check 7 only compares the Output Template to the template file — it wouldn't catch an internal skill drift where the prose lists `### 1. Foo` but the output template shows `## 1. Bar`. This is a narrower but still load-bearing contract: LLM reads both and will produce incoherent output if they disagree. R1 residual risk from evaluation.md.
- Add a `spec/bootstrap/lib/test-helpers.sh` with `inject_heading_line` / `restore_file` helpers for negative-test drift injections. Would prevent the AC-6-style substring-match test-construction bug in future checks. Low priority — only worth doing if we add 2+ more negative tests.
- **Audit `spec/templates/evaluation.template.md` (and all provenance-bearing templates) for bolded field labels.** Surfaced during the strict re-run of this task: the inline-compat `evaluation.md` had `- **Verdict**: **PASS**` (bolded), which is invisible to `provenance_read_field`'s regex `^[[:space:]]*-[[:space:]]*Verdict:` in `spec/bootstrap/lib/provenance.sh`. The checker parses the line as blank and `validate-isolation.sh:124` then blocks with "must record a final verdict before human close". Any artifact following the bolded template form silently fails strict-mode validation. Fix candidates: (a) change the template to unbolded `- Verdict: PASS`, OR (b) update the regex in `provenance_read_field` to tolerate a leading `**` prefix on the field label. Option (a) is the lower-risk fix; option (b) is more forgiving but widens the parser's accepted grammar. Apply the same audit to all `- Role:` / `- Isolation mode:` / `- Agent ID:` / `- Fallback policy:` / `- Fallback reason:` fields across `verification.template.md` and `evaluation.template.md`.
- **Provenance values must be single-token enums, not human-readable justification.** The inline-compat version of this task's `verification.md` wrote `Isolation mode: compat (Low-risk, inline in main context; no need for strict subprocess isolation for grep/diff-only checks)`. After `provenance_normalize_value` this becomes `compat_(low-risk,_inline_in_main_context;_no_need_for_strict_subprocess_isolation_for_grep/diff-only_checks)`, matching neither `strict` nor `compat`. The Stop hook caught it, but only *after* the task was marked complete. Fix candidates: (a) add a schema check in `validate-artifact.sh` that explicitly rejects multi-token values for enum fields (Isolation mode, Execution context, Role, Verdict) so the failure fires at write-time rather than at Stop-hook-time; (b) document in `spec/protocol/role-contracts.md` that justification prose must live in `Fallback policy` / `Fallback reason` / blockquote, never inline with the enum value. Both are cheap. (a) is load-bearing because it catches the class of errors I made in this task — the prose-next-to-enum habit is a natural-language reflex that needs a hard guard.
- **`profile.local.yaml` absence silently defaults to strict without announcing it.** The repo has no `profile.local.yaml` at all — `profile_read_mode` falls back to `strict` as the hard-coded default at `spec/bootstrap/lib/profile.sh:36`. That's the right default, but there's no startup log, no `show-context.sh` field, and no `session-start` hook message that tells the user "profile.local.yaml not found; defaulting to strict for verification and review". If the user assumes compat (as I did when choosing to work inline), the mismatch is only discovered at Stop-hook time, which is too late. Fix candidate: have `session-start` or `start-task.sh` print the resolved isolation modes at task-start time — one line like `[isolation] verification=strict (default) review=strict (default)` would have prevented this entire thread.
