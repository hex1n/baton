# Retrospective: root-readme-standardization

## 1. 结果

- 关闭状态: `complete`
- 主要阻塞: 无功能性阻塞；仅保留已接受的残余风险，即 README 自检只校验结构和关键术语，不覆盖全文语义等价
- 人工决策: 确认将该残余风险视为可接受，并关闭任务

## 2. 有效做法

- 把 retrospective 里的建议拆成“脚本机制 + 治理规则 + 主自检接入”三层，比只改文档更稳
- 复用 `check-consistency.sh` 作为主入口，比单独新增一个容易被忘记的检查命令更有效
- 在两份根目录 README 顶部增加轻量维护提示，能把治理规则直接暴露给最常编辑入口文档的人

## 3. 失败点

- 根目录 README 双语布局此前已经落地，但直到这次才真正形成自动检查，说明第一次任务只完成了“建立结构”，没有完成“固化维护机制”
- README 双语检查目前仍是结构级校验，不会自动发现中英文表述含义悄悄漂移

## 4. 仓库特定经验

- 对 baton 这类同时面向中文和英文读者的仓库，根目录入口文档最好明确分成英文主 README 和中文正式副本，并把两者的维护规则写进治理摘要
- 根目录入口文档的稳定性值得纳入仓库 invariant，因为它直接影响外部仓库如何接入 harness

## 5. Harness 经验

- 文档入口类需求确实适合按 harness 流程执行；这次如果没有 `requirements`、`architecture` 和 `verification`，最后大概率还是会停在“口头约定”
- retrospective 中的经验如果不立即回灌成 gate、脚本或治理规则，很容易再次退回人工记忆

## 6. 可标准化候选

- 后续可以把 `check-root-readme-bilingual.sh` 扩展成一个更通用的“入口文档检查”框架，但当前仓库规模下没必要先泛化
- 如果未来开始维护更多双语根目录文档，再考虑把贡献约定从 `CLAUDE.md` 提炼到独立 `CONTRIBUTING.md`
